# Автообновление для Windows — дизайн

Дата: 2026-11-15 · Статус: реализовано · Основа: [known-issues.md](../../known-issues.md)
«Must be done before updates are enabled», §9.3 [дизайна 0.1.0](2026-11-09-timetracker-design.md)

## 1. Зачем

Механизм обновлений есть с 0.1.0, но выключен. Без него человек узнаёт о новой версии
только случайно: заходит на страницу релизов, скачивает `setup.exe` и ставит руками.
Нужно, чтобы установленная на Windows программа сама находила **стабильный** релиз,
проверяла его подлинность и ставила по одной кнопке.

Сейчас CI сам публикует только предрелизы `-rc.N`. Финальные релизы автор собирает руками
из артефактов CI. После этой работы финальный релиз тоже готовит CI, а кнопка
**Publish** на GitHub становится моментом раскатки обновления.

## 2. Цели

- Установленная Windows-сборка (setup.exe) проверяет наличие нового стабильного релиза,
  скачивает установщик, проверяет его и ставит, а затем запускается уже новой версией.
- Предрелизы (`-rc.N`) никогда не предлагаются как обновление: ни людям со стабильной
  версией, ни тем, у кого стоит rc. У них rc обновляется до финального релиза своей ветки.
- Закрыть все пункты из known-issues «Must be done before updates are enabled»:
  - подписанный манифест, без отката на старую версию;
  - pre-release версии;
  - временный файл;
  - параллельные проверки;
  - вынос обновлений из `controllers/settings.rs`.
- Финальный тег `vX.Y.Z` → CI создаёт **черновик** релиза со всеми файлами
  и подписанным манифестом. Автор проверяет черновик и жмёт Publish.

## 3. Не цели

- Linux и macOS. `update_config()` вне Windows по-прежнему `None`. Это решение
  [дизайна кросс-платформы](2026-11-11-cross-platform-design.md).
- Подпись Authenticode: платного сертификата нет. Скачанный программой файл не получает
  Mark-of-the-Web, поэтому SmartScreen при обновлении обычно не появляется. Это не гарантия.
- Каналы обновлений (beta/rc для желающих), дельта-обновления, фоновая установка без
  согласия пользователя, принудительные обновления.
- Обновление сборок 0.1.0–0.3.0: в них обновления выключены при компиляции. Их владельцы
  один раз обновятся вручную.

## 4. Анти-цели (провал, даже если «работает»)

- Программа ставит файл, подлинность которого не доказана подписью автора.
- Обновление теряет данные или идущий таймер.
- Программа сама по себе ставит обновление без нажатия кнопки.
- Обновление предлагается бесконечно: установленная версия считает себя старее манифеста.

## 5. Как это устроено

### 5.1 Источник: файлы последнего стабильного релиза

Адрес манифеста вшивается при сборке (как сейчас, `TT_UPDATE_URL`):

```
https://github.com/OlegFM/timetracker/releases/latest/download/manifest.json
```

GitHub отдаёт по `releases/latest/…` файлы последнего **опубликованного не-предрелиза**.
Поэтому черновики и rc в этот канал не попадают, и отдельный сервер не нужен. Рядом с
манифестом лежит отделённая подпись `manifest.json.sig` (тот же адрес, `.sig` в конце).

### 5.2 Манифест и подпись

`manifest.json` — маленький JSON:

```json
{
  "version": "0.4.0",
  "url": "https://github.com/OlegFM/timetracker/releases/download/v0.4.0/TimeTracker-0.4.0-setup.exe",
  "sha256": "<64 hex, нижний регистр>",
  "page": "https://github.com/OlegFM/timetracker/releases/tag/v0.4.0"
}
```

`manifest.json.sig` — base64 (standard) от ed25519-подписи **точных байтов**
`manifest.json`.

Подпись покрывает файл целиком: версию, адрес, контрольную сумму и страницу релиза.
Поэтому старый подписанный установщик нельзя выдать за более новую версию. Канонизация
JSON не нужна, а новое поле в будущем подписывается автоматически. Поле `notes` из
нынешнего формата убирается: оно нигде не показывается.

Порядок проверки в программе:

1. Скачать `manifest.json` (лимит 64 КиБ) и `.sig`.
2. Проверить подпись над байтами через `verify_strict`. Если не сошлось — ошибка «signature».
3. Только теперь разобрать JSON и сравнить `version` с текущей версией.
4. При установке скачать `url` (https, лимит 512 МиБ, как сейчас) и сверить sha256.
   Повторная подпись установщика не нужна: sha256 уже подписан.

Формат можно менять свободно: ни одна выпущенная сборка с включёнными обновлениями ещё
не существует.

### 5.3 Версии

- **Текущая версия программы** берётся из `TT_BUILD_VERSION`, если CI его задал при сборке
  (тег без `v`, например `0.4.0-rc.1`). Иначе берётся `CARGO_PKG_VERSION`. Эта же строка
  показывается в «О программе». Без этого rc-сборка считала бы себя финальной `0.4.0`
  и не получила бы релиз 0.4.0.
- **Сравнение** — упрощённый SemVer без новой зависимости:
  - сначала числовое ядро `X.Y.Z` (недостающие части = 0, ведущая `v` допускается);
  - при равном ядре версия без суффикса новее версии с `-суффиксом`;
  - суффиксы сравниваются по частям через точку: числовые части как числа, остальные как
    строки, а числовая часть младше строковой.
  - Неразбираемая строка → «не новее»: обновление не предлагается.
  - Примеры: `0.4.0-rc.1 < 0.4.0-rc.2 < 0.4.0-rc.10 < 0.4.0 < 0.4.1`.
- **CI-проверка версии.** На любом теге ядро версии из тега должно совпадать с версией
  workspace в `Cargo.toml`. Если нет — сборка падает. Это защищает от анти-цели
  «бесконечное обновление».

### 5.4 Установленная копия или portable

Установленная копия лежит рядом с `uninstall.exe`, который пишет NSIS. Признак:
`current_exe()` → в той же папке есть `uninstall.exe`.

- **Установленная:** кнопка «Установить» (как сейчас).
- **Portable:** вместо установки кнопка «Открыть страницу загрузки». Она открывает `page`
  из подписанного манифеста в браузере. Портативную папку программа не трогает.

### 5.5 Установка

1. Скачать установщик в `%TEMP%\TimeTracker-update.exe`. Имя фиксированное: удалённые
   данные не выбирают путь. Файл появляется только после проверки, как сейчас.
2. Запустить его с ключами `/S /UPDATE` и выйти из программы.
3. В NSIS-установщике:
   - `/S` — тихая установка в ту же папку (`InstallDirRegKey`);
   - уже существующий `CLOSE_APP` дожидается выхода программы, а в тихом режиме
     завершает её принудительно, если та не вышла за 3 с. Идущий таймер хранится в
     базе, данные не теряются;
   - новый `/UPDATE` — после успешной установки запустить `tt-app.exe`. Без `/UPDATE`
     тихая установка (например, админом) программу не запускает.
4. При следующем старте программа удаляет оставшийся `%TEMP%\TimeTracker-update.exe`.
   Ошибка удаления игнорируется: файл может быть ещё занят, удалим в следующий раз.

### 5.6 Когда проверять

- При старте, если включено «Проверять обновления автоматически». Проверка тихая:
  сообщение появляется, только если обновление найдено.
- Пока программа работает (она живёт в трее неделями), — ещё раз раз в 24 часа, тоже
  тихо. *(Моё решение.)*
- Кнопка «Проверить» — с сообщением о результате.
- Одновременно идёт не больше одной проверки или загрузки. Повторный вызов во время
  `CHECKING`/`DOWNLOADING` ничего не делает.
- Найденное обновление: тост «Доступна новая версия», в настройках «Версия X доступна»
  + кнопка (§5.4) + ссылка «Что нового» (`page`).

### 5.7 Код

- `tt-services/src/update.rs`:
  - новый формат манифеста и проверка подписи над байтами;
  - `is_newer` с pre-release;
  - функция «текущая версия»;
  - признак установленной копии принимает путь, чтобы его можно было тестировать.
- `tt-app/src/controllers/updates.rs` — новый контроллер. Сюда переезжают из
  `settings.rs` проверка, установка, таймер 24 ч, guard и очистка temp-файла.
  Backup/restore пока остаются в `settings.rs`, пункт в known-issues сужается до них.
  *(Моё решение: делим то, что всё равно трогаем.)*
- Инструмент подписи — бинарник `tt-release` в `tt-services` (`src/bin/`). Он использует
  тот же код формата, что и программа, поэтому формат описан в одном месте. Подкоманды:
  - `pubkey` — печатает hex публичного ключа;
  - `manifest <version> <installer.exe> <url> <page> <out-dir>` — пишет `manifest.json`
    и `manifest.json.sig`.
  - Приватный ключ читается **только** из переменной окружения `TT_UPDATE_SIGNING_KEY`
    (32-байтный seed, 64 hex), никогда из аргументов.
  - В `tt-app` бинарник не попадает.

### 5.8 CI и релиз

- Job `installer` (Windows), на любом теге `v*`:
  - проверка версии (§5.3);
  - сборка с `TT_BUILD_VERSION`, `TT_UPDATE_URL`, `TT_UPDATE_PUBKEY`;
  - NSIS;
  - если задан `TT_UPDATE_PUBKEY`, то обязателен secret `TT_UPDATE_SIGNING_KEY`,
    `tt-release pubkey` должен совпасть с переменной (иначе падение), и `tt-release
    manifest` кладёт оба файла в артефакт. Secret доступен только этому шагу.
- Job `prerelease` становится `release`:
  - тег с `-rc.` → опубликованный предрелиз (как сейчас);
  - тег без `-` → **черновик** релиза (`--draft`) со всеми файлами трёх систем,
    манифестом и подписью;
  - другие теги с суффиксом (`-beta.N`) → тоже предрелиз.
- Раскатка = Publish черновика. Откат плохого релиза: выпустить исправленный `X.Y.Z+1`.
  Срочная мера — пометить релиз как pre-release, тогда `latest` снова указывает на
  предыдущий. Программы, уже получившие плохую версию, назад не откатываются
  (`is_newer`), им нужен исправленный релиз.
- Форки без ключей: переменные пустые → обновления выключены, манифест не создаётся,
  всё остальное собирается как раньше.

### 5.9 Ключи (делает автор, один раз)

- Seed: 32 случайных байта в hex. Команда для PowerShell 7 будет в
  `docs/development.md`.
- Публичный ключ: `cargo run -p tt-services --bin tt-release -- pubkey`.
- В репозитории:
  - secret `TT_UPDATE_SIGNING_KEY`;
  - variables `TT_UPDATE_PUBKEY` и `TT_UPDATE_URL`.
- Seed хранить ещё и в менеджере паролей. Если ключ потерян, выпущенные сборки уже не
  смогут обновиться и потребуется ручная переустановка с новым ключом.

## 6. Тесты и проверка

- **Юнит-тесты** (`update.rs`):
  - подпись: верная, байт изменён, чужой ключ, мусор в `.sig`;
  - манифест: подпись проверяется до разбора; http-адрес отклоняется;
  - `is_newer`: таблица из §5.3, включая неразбираемые строки;
  - признак установленной копии на временной папке;
  - круг `tt-release manifest` → проверка библиотекой;
  - лимит размера манифеста.
- **Контроллер:** guard от параллельных проверок — как чистая функция состояния, если
  получится без UI.
- **CI:** проверка версии и сверка публичного ключа (§5.8).
- **Ручная проверка** (в `docs/qa-checklist.md`), до первого финального релиза с ключами:
  - локальная сборка версии `0.0.1` с `TT_UPDATE_URL` на манифест конкретного rc
    (`releases/download/vX.Y.Z-rc.N/manifest.json`);
  - установить, нажать «Проверить», затем «Установить»;
  - программа закрылась, тихо обновилась, запустилась новой версией, таймер на месте;
  - то же для portable — открылась страница релиза.
